# [Feature] Runner 接入 Octopus MCP 服务提升 Runtime 综合分析与服务能力

## 背景

PSOP Runtime 运行过程中，Runner 需要结合当前 Skill、执行状态、历史交互以及用户提供的文字、图片等信息，理解用户正在做什么、遇到了什么情况，以及接下来最需要得到什么帮助。

当前 Runner 主要依靠已有上下文和模型本身进行判断。在需要理解现场画面、识别操作对象、分析视频内容或处理其他视觉信息的场景中，Runner 可利用的信息和能力仍然有限，可能出现需求理解不充分、下一步建议不准确或服务方式不够贴合现场的问题。

Octopus 正在开发，并计划通过 MCP 服务逐步提供多种视觉和内容处理能力。当前已明确的方向包括图片中部件的识别、定位和标注，后续也可能扩展到视频识别或其他图像处理任务。本期希望让 Runner 连接 Octopus MCP 服务，由 Runner 根据具体任务综合分析并按需使用合适的 Octopus 能力，从而更好地理解用户需求并提供服务。

## 当前实现与约束

- Runner 已经能够读取 Skill、Runtime 状态和终端交互上下文，并输出运行时建议。
- Runtime 和 Execution Graph 仍是正式运行步骤和状态的事实来源。
- 用户不需要新增特殊输入格式；Runner 应根据现有上下文判断是否需要进一步处理。
- Octopus 是持续开发中的外部能力服务，当前能力和后续扩展不在本 Issue 中固化为单一用途。
- Octopus 返回的是辅助观察或处理结果，不能替代 Runner 的整体判断，也不能直接修改 Runtime 状态。

## 核心判断

Runner 接入 Octopus 后，交互方式应从固定流程改为综合分析和按需使用：

```text
Runtime 上下文 + 用户交互
  -> Runner 综合理解当前任务和用户需求
  -> Runner 判断是否需要 Octopus，以及需要哪类能力
  -> Runner 连接 Octopus MCP 服务并获取相关结果
  -> Runner 结合 Skill、Runtime 事实和 Octopus 结果继续判断
  -> 向用户提供更合适的解释、下一步建议或辅助结果
```

Runner 负责理解任务、选择调用时机、选择合适的能力、解释结果并形成服务；Octopus MCP 服务负责提供相应的视觉或内容处理结果。无论结果是什么，正式步骤、风险判断和 Runtime 状态仍由 PSOP 原有机制负责。

## 目标

1. 将 Octopus MCP 服务接入 Runtime Agent Harness，作为 Runner 可按需使用的外部能力来源。
2. Runner 能根据上下文综合判断是否需要 Octopus，而不是每次运行都强制调用。
3. Runner 能根据具体任务选择合适的 Octopus 能力，不将其用途限制为单一的图像识别场景。
4. Runner 能理解并综合 Octopus 返回的图片、视频或其他视觉处理结果。
5. Runner 能利用这些结果更准确地判断用户需求、组织下一步建议和提供适当的辅助信息。
6. 当 Octopus 不可用、结果不明确或不适合当前任务时，Runner 仍能基于已有上下文继续提供服务。
7. 保持 Runtime 状态、Execution Graph 和现有安全约束不被外部能力调用绕过。

## 非目标

- 本期不要求用户新增固定的提问、上传或交互步骤。
- 本期不让 Octopus 代替 Runner 成为最终对话和决策主体。
- 本期不让 Octopus 直接修改 Session、Execution Graph、Terminal Event 或 Skill 内容。
- 本期不允许模型根据外部处理结果绕过正式状态任意跳步。
- 本期不涉及 Octopus MCP 服务本身的开发和具体能力设计。
- 本期不要求一次性覆盖 Octopus 未来的所有能力，优先验证 Runner 的综合分析和按需调用机制。

## 用户流程

1. 用户按照原有方式使用 Runtime，不需要学习新的特殊输入格式。
2. Runner 持续结合 Skill、运行状态、历史交互和当前输入理解任务。
3. 当 Runner 认为现有信息不足，或判断外部视觉/内容处理能够改善回答时，按需使用 Octopus MCP 服务中的相关能力。
4. Runner 将 Octopus 的结果与原有上下文进行综合，而不是直接转发外部结果。
5. Runner 向用户提供下一步建议、解释、确认问题或适合的辅助结果。
6. 用户继续操作，Runner 根据新的交互和运行事实持续更新判断。

## 功能要求

- Runtime Agent Harness 应以受控方式连接 Octopus MCP 服务，并记录 Runner 对其能力的使用情况。
- Runner 应自主判断调用时机和所需能力，避免无必要、重复或与当前任务无关的调用。
- Runner 应明确区分用户输入、Skill 约束、Runtime 事实和 Octopus 返回的辅助结果。
- Runner 应将外部结果转化为用户可理解的服务内容，不能把未经解释的内部结果直接展示给用户。
- 当结果不清晰、与上下文冲突或不足以支持判断时，Runner 应表达不确定性并采取补充询问、文字指导或安全降级。
- 图片部件标注、视频识别及其他视觉处理结果都只能作为辅助信息，不能自动证明用户已完成操作。
- 复杂或高风险操作仍需遵守 Skill 中的安全说明和人工确认要求。
- 外部能力调用应遵守现有 Agent Harness 的权限、资源和错误处理规则。

## 失败处理与安全边界

- Octopus 不可用、超时或返回失败时，Runner 应继续使用已有上下文提供有限但诚实的帮助。
- Octopus 返回多个可能解释、无法确定目标或处理结果不完整时，Runner 不应伪装成确定结论，应向用户说明不确定性或请求更多信息。
- 用户内容和外部结果均属于不受信任输入，不能覆盖系统、Skill 或 Runtime 的安全约束。
- Runner 不得把 Octopus MCP 服务暴露为不受限制的通用执行能力。
- 外部能力调用不应改变 Runtime 的正式状态；所有状态推进仍由 Runtime 的确定性逻辑完成。
- 不向用户泄露内部实现细节、隐藏提示、错误细节或无关上下文。

## 验收标准

- [ ] Runner 可以在 Runtime 中连接 Octopus MCP 服务，并按需使用其可用能力。
- [ ] 用户无需改变原有使用方式即可使用 Runtime 流程。
- [ ] Runner 能根据上下文判断是否需要外部处理，以及需要哪类能力。
- [ ] Runner 能正确理解并综合 Octopus 返回的不同类型结果。
- [ ] 使用 Octopus 后，代表性现场任务的需求理解、下一步建议和用户可理解性得到改善。
- [ ] Octopus 不可用或结果不明确时，Runner 能安全降级并表达不确定性。
- [ ] Octopus 返回的结果不会直接修改 Runtime 状态或绕过 Execution Graph。
- [ ] 外部处理结果不会自动进入用户证据或证明步骤完成。
- [ ] 能够在现有 Trace / Observability 中追溯 Runner 的调用、结果和降级情况。

## 测试要求

### Runner

- 有图片且需要理解现场对象时，Runner 能判断使用 Octopus 有帮助并综合结果。
- 有视频或其他视觉材料时，Runner 能根据任务需要选择是否使用 Octopus，而不是假定固定处理方式。
- 只有文字或已有上下文足够时，Runner 不进行不必要的外部调用。
- Octopus 返回不确定、冲突或无法处理的结果时，Runner 能正确表达限制。
- Runner 能根据外部结果调整下一步建议，但不会自行修改正式运行步骤。

### Agent Harness

- 验证能力发现、权限判断和错误处理符合现有 Harness 约束。
- 验证外部调用的成功、拒绝和失败情况能够被正确处理和观察。
- 验证外部描述或返回内容不能覆盖系统指令和 Skill 安全约束。

### Runtime 与端到端

- 验证外部能力调用前后 Runtime 状态、Execution Graph 和 Replay 事实保持一致。
- 验证文字指导、视觉处理结果和安全提示能够被用户正常看到。
- 使用安装、维护或故障排查类 Skill 验证以下闭环：

```text
用户按原有方式操作
  -> Runner 综合理解当前需求
  -> Runner 按需使用 Octopus MCP 服务
  -> Runner 综合结果并提供更合适的服务
  -> 用户继续操作
```

## 文档同步

- 更新 Runner 和 Runtime 的能力说明，明确 Runner 按需使用 Octopus MCP 服务。
- 更新 Agent Harness 连接 MCP 服务及使用其能力时的安全边界说明。
- 更新图片、视频及其他外部处理结果在 Runtime 中的使用说明。

## 完成定义

Octopus MCP 服务接入 Runner 后，Runner 能在不改变用户原有使用方式的前提下，根据 Runtime 上下文和用户交互综合判断是否需要外部视觉或内容处理，并选择合适的 Octopus 能力来更好地理解用户需求、组织下一步建议和提供辅助服务；同时，Runtime 的正式状态与安全边界仍由 PSOP 原有机制负责，外部能力调用不会绕过或替代这些机制。
